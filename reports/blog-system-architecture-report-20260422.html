03 Flow

End-to-end publishing sequence

This is the actual control path from scheduled execution to a public article URL.
01

Cron starts the worker wrapper

The worker crontab runs /root/workspace/generate-tech-article.sh twice daily. That wrapper logs start and finish markers into /root/workspace/tech-article-automation.log and delegates into the repo-backed pipeline.

Current schedule: 00:00 and 14:00 on the worker.
02

The repo wrapper resolves Python and launches the runner

research-department/generate-tech-article.sh selects the virtualenv Python when available and executes runners/publish_from_topic_file.py.

03

Topic rotation chooses a non-duplicate idea

The runner reads the topic file, loads the persistent topic state, pulls recent WordPress titles, and skips candidate topics that are too similar to recent posts.

Key control: Similarity is evaluated before the expensive generation stages begin.
04

Research fetch builds a grounded source packet

The crew generates multiple search queries, hits Tavily, deduplicates URLs, fetches source pages, and writes a normalized research packet into the run directory before any article drafting happens.

05

Model-routed writing stages produce structured artifacts

The system calls the configured model for research synthesis, body writing, JSON draft composition, humanization, and editorial review. Responses are parsed back into typed Pydantic artifacts.

Transport: HTTP, local OpenClaw CLI, or SSH bridge depending environment and model family.
06

Lint, duplicate detection, and editorial scoring gate the publish

The draft must satisfy excerpt length, minimum word count, source count, citation coverage, H2 count, safe category mapping, tag presence, image prompt presence, and qualitative editorial thresholds.

07

Revision loop runs automatically if the draft is not ready

If the audit fails, the system feeds revision notes back into the humanizer and tries again, up to the configured revision limit. This prevents weak first drafts from publishing immediately.

08

Publish step writes directly into WordPress

The publish tool renders markdown to HTML, uses Docker to run PHP inside the WordPress container, inserts or resolves categories and tags, creates the post, and optionally triggers a remote featured-image generation step.

09

Verify step confirms live integrity

After publishing, the verify tool fetches the post through the WordPress REST API and checks live URL, author ID, featured media presence, status, and excerpt properties.

10

Run artifacts stay on disk for debugging and traceability

Each run writes raw model outputs, parsed artifacts, lint results, audit rounds, publish metadata, verification results, and a linear run.log timeline into the run directory.

04 Generation Layer

How the content pipeline is designed

The design is intentionally split into narrow stages so failures, malformed JSON, or weak editorial outputs do not automatically leak into production.

Config and environment resolution

The settings layer loads shared OpenClaw secrets, repo-local overrides, model aliases, transport configuration, WordPress target information, article thresholds, and topic-file paths. The same codebase can run on the worker or locally.

Research stage

Search is grounded in Tavily results, not in model memory alone. The pipeline fetches actual page text and requires a minimum source count, preserving URLs through to the final citation list.

Structured artifact flow

Research, draft, editorial review, publish metadata, and verify results all pass through typed schemas. This lowers ambiguity between stages and makes the run directory inspectable.

Model routing

Friendly stage-level model names are decoupled from the actual runtime provider. The router can map to local models or GPT-class models without changing the orchestration logic.

Quality gates

Draft lint blocks missing citations, missing image prompts, unsafe categories, weak structure, placeholder text, thin intros, and article titles that are too close to source titles.

Publish safety

The publish only occurs when the combined audit passes. The latest validated run demonstrates the intended behavior: first audit failed, revision loop ran, second audit passed, then publish executed.

05 Presentation Layer

How the public WordPress side works

The frontend is a custom dark editorial theme, not a stock WordPress layout. It combines visual presentation with several content and conversion behaviors.

Editorial homepage and archive logic

The homepage chooses a featured lead set, computes a separate article river with offsets, surfaces top categories, and adds collection cards and a utility sidebar. Archive, search, category, tag, and author views are all adapted to the editorial framing.

Single article conversion loop

Single posts include the hero, article metadata, inline newsletter conversion module, share actions, author box, post-bottom continuation band, previous/next reading links, related posts, and comments.

Newsletter capture path

The theme injects hidden admin-post fields into newsletter forms, validates nonces, uses a honeypot field, detects duplicates, stores subscribers in a WordPress option, and exposes an admin export page for captured emails.

SEO and routing controls

Search pages and low-value thin archive routes emit noindex. Author requests are normalized so valid author slugs resolve consistently while invalid author paths fail cleanly instead of degrading to generic output.

06 Ops and controls

Deployment, smoke tests, and operating safeguards

The system separates theme deployment from article publishing. Theme code is deployed by rsync and smoke-tested, while article publishing happens through the worker pipeline.

Theme deployment

scripts/deploy-theme.sh rsyncs the local theme into the live WordPress theme directory on the worker, creates a remote backup, normalizes permissions, and optionally runs smoke tests.

Public smoke tests

scripts/smoke-test.sh checks the live homepage, archive page, category archive, and search route for expected markers. It validates the public surface without requiring WordPress admin access.

Run traceability

Every generation run writes raw and parsed stage outputs. This makes stage stalls, weak drafts, failed audits, and publish metadata visible without digging into model providers directly.

09 Design assessment

Strengths, tradeoffs, and risk concentration

The system is functional and increasingly disciplined, but some runtime dependencies remain concentrated.

What is strong

The architecture separates generation from presentation, preserves run artifacts, uses real research instead of pure prompting, and does not publish until both lint and editorial review agree.

What is concentrated

The generation path depends on external model routing and on the worker plus OpenClaw auth plane remaining reachable. Slow remote model stages can stretch end-to-end publish latency significantly.

What to watch

The biggest system-level risks are model transport stalls, worker-side cron drift, WordPress container path assumptions in the publish tool, and quality heuristics that may still allow stylistic repetition even after passing.

Bottom line: this is a real multi-stage publishing system, not a thin script. It already demonstrates revision-gated publishing, theme-level conversion logic, deployment discipline, and operational traceability. The next maturity step would be deeper host-independent observability around slow model stages and worker run retention.
